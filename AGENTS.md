Do NOT activate when:

---

## Testing Principles

1. **Test Behavior, Not Implementation Details**:
   Assert on inputs and observable outputs/side-effects rather than inspecting private state or internal method calls.
2. **Deterministic & Isolated**:
   Each test must run independently in any order without relying on shared mutable state or sleep timers.
3. **The Testing Pyramid**:
   - 70% Unit Tests: Fast, isolated, test pure business logic and edge cases.
   - 20% Integration Tests: Test module interactions, database queries, and boundary adapters.
   - 10% E2E / Smoke Tests: Verify critical user journeys end-to-end.
4. **Arrange-Act-Assert (AAA)**:
   Clearly separate the setup, action, and assertion phases in every test case.

## Standard TDD Workflow

1. **Write Failing Test (Red)**:
   Draft the test describing the expected behavior and verify that it fails for the expected reason.
2. **Implement Minimal Code (Green)**:
   Write the simplest implementation that makes the test pass.
3. **Refactor**:
   Clean up code design, eliminate duplication, and verify tests remain green.

## Edge Case Coverage Matrix

When writing tests for any function or endpoint, verify the following inputs:
- **Null / Undefined / None / Nil**
- **Zero Values & Empty Collections**: `0`, `""`, `[]`, `{}`
- **Boundary Conditions**: Max allowed length, off-by-one indices, negative integers
- **Malformed Inputs**: Invalid email formats, malformed JSON, out-of-range dates
- **Failure States**: Upstream timeouts, network failure, disk write errors

## Safety Principles (Zero Data Loss)

1. **Check Working State Before Mutating**:
   Always run `git status` and `git diff --stat` before branch switches, rebases, or resets.
2. **Never Stash Blindly**:
   If uncommitted work exists, either create a temporary commit (`git commit -m "wip: save state"`) or name your stash explicitly (`git stash push -m "feature-backup-2026-10-27"`).
3. **Reflog as Safety Net**:
   Before any forced operation or hard reset, note `git rev-parse HEAD`. You can always restore to that SHA via `git reset --hard <sha>` if needed.
4. **Interactive Rebases**:
   Never rebase public/shared branches that other team members are actively tracking. Only rebase local feature branches.

---

## Core Workflows

### 1. Preparing Clean Feature Branches
```bash
# 1. Fetch latest remote state
git fetch origin

# 2. Rebase feature branch on top of main/master
git checkout feature/my-feature
git rebase origin/main

# 3. If conflicts arise, examine the conflicted files
git status
```

### 2. Conflict Resolution Protocol
1. Identify conflicting files marked with `both modified:`.
2. Inspect markers:
   - `<<<<<<< HEAD` (current branch changes)
   - `=======` (separator)
   - `>>>>>>> <branch-or-commit>` (incoming changes)
3. Edit the file to integrate both sets of changes cleanly without losing intent.
4. Run tests or linter to ensure syntax and tests pass.
5. Stage the resolved files: `git add <file>`.
6. Continue rebase/merge: `git rebase --continue` (or `git merge --continue`).
7. **Never** use `git rebase --skip` unless you deliberately intend to discard the entire commit.

### 3. Atomic Conventional Commits
Structure each commit to represent one logical change:
```bash
# Format: <type>(<scope>): <short imperative summary>
# Types: feat, fix, docs, style, refactor, perf, test, build, ci, chore
git commit -m "feat(auth): add OAuth2 refresh token rotation"
git commit -m "fix(api): handle timeout when upstream service is unreachable"
git commit -m "test(cart): add edge cases for expired coupon codes"
```

### 4. Git Worktrees for Parallel Branch Contexts
Instead of stashing or cloning multiple times, use Git Worktrees:
```bash
# Create a parallel workspace for a hotfix while keeping feature work intact
git worktree add ../project-hotfix main
cd ../project-hotfix
# Perform fix, commit, and push
# Remove worktree when done
cd -
git worktree remove ../project-hotfix
```

### 5. Git Bisect for Automated Regression Hunting
```bash
git bisect start
git bisect bad                 # Current commit is broken
git bisect good v1.2.0         # v1.2.0 was known good
# Git checks out intermediate commits. Test each:
git bisect run npm test        # Fully automated bisect run
git bisect reset               # Return to original HEAD
```

---

## Review Methodology: The 5-Pillar Audit

Evaluate all changes against five structured dimensions:

1. **Correctness & Logic**:
   - Does the implementation fulfill the intended requirements?
   - Are edge cases handled (null/undefined, zero-length arrays, network timeouts, race conditions)?
2. **Security & Vulnerabilities**:
   - Are inputs sanitized/validated at boundary layers?
   - Any secret leaks, SQLi, XSS, CSRF, or insecure deserialization?
   - Are authorization and authentication checks enforced before data access?
3. **Performance & Scalability**:
   - Any N+1 query patterns, unintentional $O(n^2)$ loops, or memory leaks?
   - Are resources (database connections, file handles, streams) released reliably?
4. **Testability & Coverage**:
   - Are there unit tests for new logic and edge cases?
   - Do existing tests still pass, or were tests silenced/deleted?
5. **Maintainability & Idiomatic Style**:
   - Is naming self-descriptive and domain-accurate?
   - Does it adhere to existing codebase architectural conventions?

---

## Feedback Formatting Standard

Categorize every review observation using standard tags:

- **`[BLOCKER]`**: Critical bug, data loss risk, or security vulnerability that must be fixed before merge.
- **`[WARNING]`**: Likely bug, performance bottleneck, or missing test case for an edge case.
- **`[SUGGESTION]`**: Clean code improvement, refactoring opportunity, or idiomatic modernization.
- **`[NIT]`**: Minor formatting, typo in comments/docs, or aesthetic preference (non-blocking).
- **`[PRAISE]`**: Recognition for well-designed abstractions, clean tests, or elegant solutions.

Each feedback comment should specify:
1. **File and Line Number**: e.g., `src/services/billing.ts:L45-L52`
2. **Issue**: What is wrong or risky.
3. **Impact**: Why it matters.
4. **Suggested Code Fix**: Provide a concrete drop-in snippet.

## Semantic Versioning (SemVer 2.0.0) Rules

Given a version number `MAJOR.MINOR.PATCH`:

1. **`MAJOR` (e.g. 1.0.0 -> 2.0.0)**:
   - Incremented when making incompatible API changes or breaking changes.
   - Conventional Commit trigger: `BREAKING CHANGE:` in footer or `!` after type (e.g., `feat!: remove deprecated v1 API`).
2. **`MINOR` (e.g. 1.0.0 -> 1.1.0)**:
   - Incremented when adding functionality in a backward-compatible manner.
   - Conventional Commit trigger: `feat: add export to CSV option`.
3. **`PATCH` (e.g. 1.0.0 -> 1.0.1)**:
   - Incremented when making backward-compatible bug fixes.
   - Conventional Commit trigger: `fix: handle null pointer in auth middleware`.
4. Non-bumping types (typically do not bump public version unless configured):
   - `docs:`, `style:`, `refactor:`, `perf:`, `test:`, `build:`, `ci:`, `chore:`.

## Step-by-Step Release Workflow

### Step 1: Validate Recent Commit Messages
Run the validator to ensure commits conform to standard format:
```bash
bash ./scripts/validate-commit-msg.sh
```

### Step 2: Determine Next Version
1. Identify the latest git tag: `git describe --tags --abbrev=0 2>/dev/null || echo "v0.0.0"`
2. Inspect all commits since that tag:
   ```bash
   git log $(git describe --tags --abbrev=0)..HEAD --oneline
   ```
3. Evaluate highest precedence bump:
   - Any `BREAKING CHANGE` or `!` -> **MAJOR**
   - Any `feat:` -> **MINOR**
   - Any `fix:` -> **PATCH**

### Step 3: Generate Changelog Entry
Execute the changelog generator script:
```bash
bash ./scripts/generate-changelog.sh v1.1.0
```

### Step 4: Tag & Publish
```bash
# 1. Update version files (e.g. package.json, pyproject.toml)
# 2. Commit release
git add CHANGELOG.md package.json
git commit -m "chore(release): v1.1.0 [skip ci]"

# 3. Create annotated Git tag
git tag -a v1.1.0 -m "Release v1.1.0"

# 4. Push branch and tag
git push origin main --tags
```
